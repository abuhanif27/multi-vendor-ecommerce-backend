# Phase 4: Payment Gateway Integration (SSLCommerz Sandbox) Design

## 1. Objective
Integrate the SSLCommerz Sandbox payment gateway into the existing Payment domain while strictly preserving the Platform Foundation v1 architecture. SSLCommerz will act purely as an infrastructure adapter.

## 2. Architecture (Infrastructure Layer)
We will introduce an infrastructure abstraction layer within the `payments` app to keep gateway logic decoupled from domain logic.

```
apps/payments/
    gateways/
        __init__.py
        base.py         # Defines abstract PaymentGateway
        sslcommerz.py   # Concrete SSLCommerzGateway implementation
        registry.py     # Gateway resolver/factory
```

**Interface Definition (`base.py`)**
```python
from abc import ABC, abstractmethod

class PaymentGateway(ABC):
    @abstractmethod
    def initialize_payment(self, payment_id: str, amount: Decimal, currency: str, customer_info: dict, return_url_base: str) -> str:
        """Returns the gateway redirection URL."""
        pass

    @abstractmethod
    def validate_payment(self, payload: dict) -> dict:
        """Validates IPN/Callback payload with the gateway server. Returns validated data."""
        pass

    @abstractmethod
    def refund_payment(self, payment_id: str, refund_id: str, amount: Decimal) -> dict:
        """Processes a refund via the gateway API."""
        pass
```

`PaymentService` will retrieve the appropriate gateway via the registry and depend solely on this abstraction.

## 4. Payment Flow Sequence
1. **Checkout:** Customer initiates payment.
2. **Init:** `PaymentService.initialize_payment()` creates a `PENDING` `Payment` record.
3. **Gateway Init:** Calls `SSLCommerzGateway.initialize_payment(...)`.
4. **Redirect:** Returns the SSLCommerz Session URL. Customer is redirected.
5. **Customer Pays:** On the SSLCommerz hosted page.
6. **Callback / IPN:** SSLCommerz sends a POST request to our API endpoints.
7. **Validation:** Endpoint routes to `PaymentService.validate_payment(payload)`.
8. **Verification API:** `SSLCommerzGateway.validate_payment()` queries the SSLCommerz Order Validation API to independently verify the transaction `val_id` and `amount`.
9. **Update State:** `PaymentService` updates `Payment.status = CAPTURED`, filling `raw_metadata` with bank references.
10. **Events:** Synchronously publishes `PaymentCapturedEvent` (Domain Event) to execute Order state transitions. Asynchronously publishes Integration Events for notifications.

## 5. Endpoints & Callbacks
New REST endpoints will be exposed under `apps/payments/api/webhooks.py`:
- `POST /api/payments/sslcommerz/success/`
- `POST /api/payments/sslcommerz/fail/`
- `POST /api/payments/sslcommerz/cancel/`
- `POST /api/payments/sslcommerz/ipn/`

All endpoints will delegate strictly to `PaymentService.process_webhook(provider='SSLCOMMERZ', payload=request.POST)`.

## 6. Database Changes
No new tables are required. The existing `Payment` model will be utilized.
- `provider`: Set to `SSLCOMMERZ`
- `provider_reference`: Stores the `tran_id` generated by us.
- `raw_metadata`: A JSON field storing `val_id`, `bank_tran_id`, `card_type`, `currency`, and the full raw payload for auditability.

## 7. Security Rules
- **Never Trust Frontend:** The frontend URL redirects are for UX only. Fulfillment happens strictly based on backend validation.
- **Independent Validation:** Every success callback must trigger a backend-to-backend request to SSLCommerz's Order Validation endpoint (`/validator/api/validationserverAPI.php`) using the `val_id`.
- **Idempotency:** Callbacks checking the same `tran_id` will check if `Payment.status` is already `CAPTURED` to avoid duplicate processing (Row-level lock on `Payment`).
- **Amount Verification:** The verified amount returned by the Validation API must exactly match `Payment.amount`.

## 8. Refunds
Phase 1 Refund Foundation remains completely intact.
- `PaymentService.process_refund` will call `SSLCommerzGateway.refund_payment()`.
- The gateway adapter will hit SSLCommerz's Refund API.
- Synchronous vs Asynchronous refund states will be managed based on SSLCommerz API responses (`SUCCEEDED` or `PENDING`).

## 9. Testing Strategy
- **Unit Tests:** `unittest.mock.patch` will be used to simulate SSLCommerz HTTP responses (`requests.post` or `requests.get`) for Init, Validation, and Refund APIs.
- **Scenarios Covered:**
  - Successful init and validation.
  - Validation failure (amount mismatch).
  - Validation failure (invalid `val_id`).
  - Duplicate IPN callback idempotency check.
  - Failed and Cancelled callback flows.
  - Refund success and failure.
